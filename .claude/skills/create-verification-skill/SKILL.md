# 検証スキルを作成する

本格的なプロジェクトには、実際のアプリを操作して動作を証明するための、スクリプト化された手段が必要になる。
アプリを起動し、ユーザーと同じやり方で機能を動かし、証跡を取得する手段である。
このスキルは、その手段をリポジトリに合わせたプロジェクトローカルのスキル(`.claude/skills/verify-<app>/`)として生成する。
生成物の読み手は人間ではなく、次に作業するエージェントである。
そのエージェントは、作業の途中でアプリを一度も見ないまま生成物を読む。

## 1. ユーザーではなくリポジトリに聞く

以下の問いには、コードベースから答える。
ユーザーに聞くのは、観察できないことだけにする。

- **Surface(操作面)**：ユーザーが実際に触れるものは何か。Web UI、CLI/TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリのどれか。複数ある場合は主たるものを選び、残りは注記する。
- **Run(起動)**：アプリはローカルでどう起動するか。リポジトリ自身が文書化している開発用コマンド(package scripts、Makefile、README のクイックスタート)を優先する。ポート、環境変数、シードデータ、認証を控える。
- **Drive(操作)**：エージェントはどうやってプログラム的に操作できるか。まず既存のハーネスを探す。Playwright/Cypress のスペック、expect スクリプト、PTY ヘルパー、curl で叩けるエンドポイント、デバッグポートなどである。それらがなければ汎用の手順を選ぶ。Web と Electron にはブラウザ/CDP、CLI/TUI には tmux/PTY ハーネス、サービスには素の HTTP を使う。
- **Observe(観測)**：どんな証跡を取得できるか。スクリーンショット、ターミナルの記録、レスポンスボディ、ログ、終了コード、DB の状態などがある。
- **Isolate(分離)**：2つのインスタンスを並べて動かせるか(ポート、データディレクトリ、プロファイル)。動かせないなら、生成するスキルにそう書く。共有インスタンスを二重に操作するのを断るほうが、ユーザーのセッションを壊すよりよい。

チェックアウトした状態でビルドも起動もできないなら、生成の前にそれを直す(または正確に報告する)。
壊れた土台に対して書いたスキルは、誤った手順を教えてしまう。
無関係なアセットの欠落が起動を妨げている場合(API が配信しない静的ディレクトリ、サンプル設定など)は、生成するスキルがそれを作成してよい。
その際は、検証用の足場であることを明示し、クリーンアップで削除する。

## 2. スキルを生成する

`.claude/skills/verify-<app>/SKILL.md` を書く。
YAML フロントマターには `name: verify-<app>` と、`description` を置く。
`description` には、アプリ名、操作面、使いどきを含める。
フロントマターがなければ、スキルは登録されない。
本文には次のセクションを置く。
どのセクションも、インタビューで実際に分かったことに基づいて書き、プレースホルダーを残さない。

- **Launch(起動)**：検証用にアプリを起動する正確なコマンドと、準備完了の見分け方(ログの1行、プロンプトなど)。Launch は、空のデータディレクトリから、マイグレーションとシードデータを含めて、使える状態に到達しなければならない。準備完了とは、プロセスが応答することではなく、使えることを指す。データベースのヘルスチェックが通っても、初期化スクリプトがまだ実行中のことがある。終了手順(teardown)も含める。短命な CLI や TUI には、常駐させるサーバーがない。その場合の Launch は、バイナリのビルド(または依存のインストール)を一度行い、操作のたびに隔離した PTY か tmux セッションを開始することを意味する。
- **Doctor(診断)**：「このインスタンスは操作する価値があるか」に答える、読み取り専用のチェックを一つ置く。プロセスが動いているか、バージョンとビルドが正しいか、ポートを自分たちが握っているか、認証が有効かを確認する。エージェントは、何かがおかしいと感じたら、まずこれを実行する。
- **Drive(操作)**：このリポジトリの実際のセレクターとコマンドで書いたハーネスの手順。例ではなく実物を書く。座標やタブ順ではなく、安定したハンドル(ARIA ラベル、data 属性、プロンプト文字列、ルートパス)を使う。
- **Evidence(証跡)**：証明のために何を取得し、どこに置くか。証明の基準も書く。内部のセッターやテスト専用のエンドポイントではなく、実際のユーザー経路を動かす。最終画面だけでなく、操作と結果の状態を取得する。目に見えるものに加えて、副作用(書き込まれたファイル、挿入された行、送信されたメッセージ)も検証する。モックを使ってよいのは、本番の境界がすでに外部システムを隔離している箇所だけである。安全な経路がドライランやテストモードであるときは、名前を信用せず、ファイル、ネットワーク、git の ref を観察して、何を実際にスキップするかを確かめる。ドライランの中には、ネットワークに触れたりブラウザを開いたりするものがある。
- **Cleanup(後片付け)**：実行が作成したインスタンスの片付け方。プロセス名で kill しない。自分が起動したものだけを kill する。Cleanup が消すのはインスタンスと一時的な状態であり、証跡は消さない。証明の成果物は、スキルが名指しした場所に、片付けのあとも残す。
- **Helpers(ヘルパー)**：スキルが同梱するスクリプトは、実行可能にし、呼び出し方を本文に示す。読み手が解読しなければならないヘルパーは、ヘルパーではない。

## 3. フィーチャーマップを作る

`.claude/skills/verify-<app>/features/README.md` と、特定できたユーザー向け機能ごとに1ファイルを作る。
最初は上位3〜5件を目安とし、ルート、コマンド、メニュー、ドキュメントから拾う。
形式は、[`references/feature-map-example/`](https://github.com/cursor/plugins/tree/main/pstack/skills/create-verification-skill/references/feature-map-example)(原典のリポジトリ)に従い、README の索引と機能ごとのファイルで構成する。
各ファイルは、ユーザーの視点から、機能とは何か、どう到達するか、ハーネスでどう操作するか、動作を証明する観測可能な最終状態は何かに答える。
H2 見出しは次の4つとする。

- `Sub-features`
- `How to get to it (user POV)`
- `Driving it with <harness>`
- `Gotchas`

シードデータに、ジャーニーが必要とする前提条件が欠けているときは、そのジャーニーは失敗を報告し、理由をその機能の `Gotchas` に書く。
通すためにジャーニーを弱めてはならない。
マップは、リポジトリが保守する検証の情報源である。
マップが他の入口を挙げているのに、都合のよい入口一つだけを操作した証明は、不完全である。

## 4. 引き渡す前に、生成したスキルで証明する

生成したスキル自身の手順を、最初から最後まで一度実行する。
起動し、診断し、マップ上の機能を「一つ」操作し、証跡を取得し、片付ける。
一つで十分である。
残りは、マップがあるおかげで、以後の実行でカバーできる。
片付けのあと、名指しした場所に証跡がまだ残っていることを確認する。
証跡を消してしまう Cleanup は、このステップに失敗している。
失敗したものは直す。
失敗した試行のたびに、生成した Cleanup も実行し、壊れた試行がプロセスやポートを取り残さないようにする。
一度も実行されていない生成スキルは、成果物ではなく下書きである。
実際の対象の代役で証明した場合(新規 VM の代わりのコンテナ、リモートスタックの代わりのローカルスタックなど)は、代役が行ったセットアップのうち、対象では行われない手順をすべて列挙する。
それらの手順は、実際の対象での実行がカバーするまで、未検証のままとする。

## 5. 保守ループを案内する

アプリの変化に合わせてマップを正確に保つために、`/maintain-verification-skill` をユーザーに案内する。
実施の頻度は、ユーザーが尋ねたときだけ提案する。
