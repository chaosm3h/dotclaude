# Notes 検証マップ

このディレクトリは、Notes のユーザー向け動作を検証するための、保守対象の一次情報です。アプリを操作する前にまずインデックスを読み、その後、該当する機能ファイルを手順書として使います。

## 基本の前提条件

- Notes を `http://127.0.0.1:4173` で起動します。データディレクトリには使い捨てのものを使います。
- 並行実行で状態が共有されないよう、`NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定します。
- タイトルが `Quarterly plan` と `Grocery list` のノートを初期データとして投入します。
- `control-notes` と `notes` CLI を `PATH` に置きます。
- `control-notes doctor` を実行し、URL、データディレクトリ、ビルドリビジョンが想定どおりであることを確認します。
- 今回の検証実行で起動していないインスタンスは、絶対に操作しません。

## 操作の規約

- 手順書の前提条件に別の指定がない限り、すべての手順を基本状態から始めます。
- CSS セレクタや DOM 上の位置ではなく、ARIA ロールとアクセシブルネームを優先します。
- コマンドはすべてリテラルとして扱います。引用符で囲まれた名前とフラグは変更しません。
- ブラウザ操作は `control-notes browser` 経由で実行します。
- ターミナル操作は `control-notes cli -- <command>` 経由で実行します。
- データを変更した後は、初期データを復元します。クリーンアップで証跡（proof artifact）を削除してはいけません。

## 証跡とスキップの報告

- 最終画面だけでなく、ユーザーの操作と、その結果の状態を記録します。
- UI の証跡には、ARIA スナップショットと、アプリを識別できるスクリーンショットを含めます。
- CLI の証跡には、コマンド、stdout、stderr、終了コードを含めます。
- 変更の証跡には、保存された値を読み取り専用の別の手段で確認した結果を含めます。
- すべての成果物に、機能 ID と使用した入口（entry point）を記録します。
- 到達できなかった経路は、試みたコマンドと、満たされなかった前提条件を添えて報告します。
- スキップした入口を、別の経路で検証したものとして報告してはいけません。

## 機能エントリの規約

各機能ファイルは、H1 のタイトルと、ユーザーから見える動作を説明する 1 段落で始めます。その後、次の 4 つの H2 セクションを、この順序で過不足なく置きます。

1. `Sub-features` には、短い ID と、各動作を 1 行で説明したものを並べます。
2. `How to get to it (user POV)` には、ユーザーが使えるすべての入口を並べます。
3. `Driving it with <harness>` は `Preconditions:` で始め、ラベル付きの箇条書きを使います。各項目では、ユーザーの操作を、正確なコマンドと観測可能な結果に対応させます。
4. `Gotchas` には、検証実行の時間を無駄にしたり、結果を無効にしたりする落とし穴を並べます。

実装の詳細はマップに書きません。書くのは、ユーザーの経路、安定したハンドル、必要な状態、コマンド、観測可能な証跡だけです。

## 機能一覧
