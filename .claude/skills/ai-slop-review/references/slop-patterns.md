# AIスロップ パターンカタログ

検出対象のパターン一覧。各パターンに「検出方法」「なぜダメか」「severityの目安」を記す。
severityは文脈で上下する。ここに書いた目安を機械的に適用せず、実害で判断すること。

## 1. 実況中継コメント

コードが読めば分かることをそのまま日本語/英語で繰り返すコメント。

```typescript
// ユーザーIDを取得する
const userId = user.id
// 結果を返す
return result
```

- **検出**: コメント行と直後のコードを見比べる。コメントを消して情報が失われなければ実況中継
- **なぜダメか**: 情報量ゼロのままコード量だけ増える。さらに悪いことに、コード変更時にコメントが更新されず嘘をつき始める。コメントは「コードに書けない理由・制約」のためにある
- **severity**: 軽傷。ただしファイルの過半がこれなら重傷(読む速度を恒常的に落とすため)

## 2. バナーコメント・過剰docstring

`// ===== Helper Functions =====` のような区切り線、シグネチャを英文に翻訳しただけのdocstring。

```typescript
/**
 * Gets the user by ID.
 * @param id - The ID of the user.
 * @returns The user.
 */
function getUserById(id: string): User
```

- **検出**: `====`、`-----`、`####` を含むコメント行のGrep。docstringは「シグネチャ以上の情報があるか」で判定
- **なぜダメか**: バナーで区切りたくなるのはファイルが長すぎる兆候であり、区切るのではなく分割すべき。中身のないdocstringはAPIドキュメント生成を汚染し、本当に説明が必要な関数を埋もれさせる
- **severity**: 軽傷

## 3. 名ばかりエラーハンドリング

catchして握りつぶす、catchしてconsole.errorだけして続行する、catchして文脈を捨てて投げ直す。

```typescript
try {
  await saveUser(user)
} catch (e) {
  console.error('Error:', e)
  // 呼び出し元は成功したと思い込む
}
```

- **検出**: `catch` のGrep後、catchブロックの中身を全数確認。「ログだけ」「空」「`throw new Error('Something went wrong')` で元エラー破棄」が該当
- **なぜダメか**: エラーが起きた事実が握りつぶされ、呼び出し元は成功したと誤認して処理を続ける。障害調査時には症状発生地点と原因地点が乖離し、デバッグコストが桁で増える。AIが「とりあえずtry/catchで包んでおく」定型を吐く典型例
- **severity**: 致命傷。データ不整合や無言の障害に直結する

## 4. 過剰防御

到達不能なnullチェック、型システムが保証済みの検証、同じ検証の多重化。

```typescript
function greet(name: string) {
  if (name === null || name === undefined) {  // 型がstringなのに
    return
  }
}
```

- **検出**: nullチェック・型チェックを見つけたら、その条件が成立し得るかを型定義と呼び出し元から判定
- **なぜダメか**: 読み手に「nullが来る経路があるのか?」と存在しない危険を調査させる。防御的returnは失敗を隠すため、本当に不正値が来たとき無言でスキップされる。「安全のため」に見えて実際は情報を破壊している
- **severity**: 軽傷〜重傷(無言スキップで失敗を隠す形なら重傷)

## 5. 過剰抽象化

実装が1つしかないinterface、1箇所からしか呼ばれないラッパー、`Manager`/`Handler`/`Service`/`Util` の空虚な階層、1メソッドのFactory。

- **検出**: interface/クラスの実装数・呼び出し箇所数を数える。「この層を消したら何が困るか」を自問し、答えが「将来のため」しかなければ該当
- **なぜダメか**: 読み手は実処理に辿り着くまで無内容な層を掘らされる。「将来の拡張性」は将来必要になったときに導入すればよく、先回りの抽象は大抵将来の要件と合わずに二重に書き直される(YAGNI)
- **severity**: 重傷

## 6. ヘッジ命名・無意味命名

`enhancedX`、`newX`、`improvedX`、`utils2`、`data`、`result2`、`processData`、`handleStuff`、`temp`。

- **検出**: `enhanced|improved|new[A-Z]|Final|2\b|temp|misc` 等のGrep。および「名前から中身が予測できるか」の目視
- **なぜダメか**: `enhanced` は「何が違うのか」を永遠に説明しない。旧版が消された後も `enhancedX` の名前だけが残り、歴史の傷跡が命名規則になる。AIが既存コードを壊さないよう並存版を作るときの典型パターン
- **severity**: 軽傷〜重傷(新旧並存で片方デッドコードなら重傷)

## 7. デッドコード・コメントアウトの残骸

未使用import、未使用変数、コメントアウトされた旧実装、到達不能分岐。

- **検出**: import/変数の参照数確認。コメントアウトされたコードはGrep(`^\s*//.*[;{})]` 等)とファイル目視
- **なぜダメか**: 読み手は「これは意図的に残されているのか」を毎回考えさせられる。コメントアウトされた旧実装はgitに履歴があるので保存価値ゼロ。AIが「念のため残しておきますね」とやる典型
- **severity**: 軽傷〜重傷(量による)

## 8. コピペ増殖

ほぼ同一の関数がパラメータ化されずに複数並ぶ。AIが「もう1つ似たものを」と頼まれて既存を複製した痕跡。

- **検出**: 類似シグネチャの関数を並べて比較。差分が1〜2箇所しかなければ該当
- **なぜダメか**: バグ修正・仕様変更のとき全コピーを漏れなく直す必要があり、1つでも漏れたら不整合バグ。コピー数に比例して保守コストが増える
- **severity**: 重傷

## 9. 型のごまかし

`any`、`as unknown as X`、`@ts-ignore`、`# type: ignore`、戻り値型の省略で実質any。

- **検出**: `\bany\b|as unknown|@ts-ignore|@ts-expect-error|type: ignore` のGrep
- **なぜダメか**: 型チェックという自動テストを局所的に無効化する。anyは伝染し、触れた変数すべての型安全を壊す。コンパイルを通すことが目的化したAIの典型的逃げ
- **severity**: 重傷。外部入力境界なら致命傷

## 10. デバッグ残骸・プレースホルダ

`console.log`、`print("here")`、`// TODO: implement`、`pass  # 後で実装`、実装されていない関数のスタブ。

- **検出**: `console\.log|print\(|TODO|FIXME|not implemented` のGrep
- **なぜダメか**: console.logは本番ログを汚染し、場合によっては個人情報を吐く。未実装スタブは「呼ぶと黙って何もしない関数」で、名ばかりエラーハンドリングと同じ毒性
- **severity**: console.log は軽傷〜重傷(出力内容による)、無言スタブは致命傷

## 11. 教科書口調コメント

`// In a production environment, you would want to...`、`// For simplicity, we assume...`、`// Note: This is a basic implementation`。

- **検出**: `production|simplicity|basic implementation|real[- ]world|実際の運用では|簡単のため` 等のGrep
- **なぜダメか**: これはチュートリアル記事の口調であり、本物のコードベースに「本番ではこうすべきですが」と書いてある時点で、そのコードは本番品質でないことの自白。やるべきことをやらず、やらなかった言い訳だけを残している
- **severity**: 重傷。スロップ純度の強いシグナル

## 12. マジックナンバー・ハードコード

説明のない数値リテラル、ハードコードされたURL・パス・認証情報。

- **検出**: 数値リテラルのGrep + 目視。`http://|https://|api[_-]?key|password|secret` のGrep
- **なぜダメか**: `86400` が「1日」なのか「たまたま同じ値の別物」なのか読み手には分からず、変更時に同値の別意味リテラルを巻き込む事故が起きる。認証情報のハードコードは論外(即漏洩事故)
- **severity**: マジックナンバーは軽傷、認証情報は致命傷

## 13. サイレントフォールバック

失敗時に黙ってデフォルト値・空配列・キャッシュを返して成功を装う。

```typescript
async function fetchUsers(): Promise<User[]> {
  try {
    return await api.get('/users')
  } catch {
    return []  // 障害がUX上「ユーザー0人」に化ける
  }
}
```

- **検出**: catch節・エラー分岐でリテラル値を返している箇所のGrep+目視
- **なぜダメか**: 障害が「データが空」という正常系の顔をして現れるため、誰も障害に気づかない。ユーザーからの「なんか空なんだけど」という問い合わせが唯一の監視になる
- **severity**: 致命傷

## 14. 幻覚API・存在しない前提

存在しないメソッド・ライブラリAPI・設定キーの使用。バージョン違いのAPI。

- **検出**: 見慣れないAPI呼び出しは実際にライブラリの型定義・ドキュメントを確認する。importが解決できるかを確認
- **なぜダメか**: 実行するまで発覚しない、あるいはビルドすら通らない。AIの学習データ由来の「それっぽいが存在しない」APIはレビューをすり抜けやすい
- **severity**: 致命傷

## 15. 絵文字・装飾

コード・コメント・ログメッセージ内の絵文字、過剰な装飾。

- **検出**: 非ASCII絵文字のGrep
- **なぜダメか**: grepしにくく、端末・ログ基盤によって化ける。ログの検索性を落とす実害がある
- **severity**: 軽傷

## 検出時の心得

- 1つ見つけたら同種を全数検索する。スロップは単発では出ない
- パターンに合致しても、文脈上の正当な理由(外部仕様、意図的な設計判断がコメントで説明されている等)があれば指摘から外す
- このカタログにない新種のスロップを見つけたら、それも遠慮なく指摘する。カタログは網羅ではなく出発点
