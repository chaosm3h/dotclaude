# 検証スキルの保守

機能マップは、アプリが変わった瞬間から陳腐化します。このスキルは、`/create-verification-skill` が生成したスキル(または、機能マップを持つプロジェクトローカルの任意の検証スキル)を保守するためのループです。厳密さの単位は、文ごとではなく機能です。すべての機能ファイルをソースから読み、すべての機能をライブで操作します。ただし、すべての箇条書きを最後まで裏取りする必要はありません。

## 結果

次のいずれかを選び、どれかを明示します。

- **clean**: すべての機能について、ソースとライブの両方でカバーできた。出荷に値する変更はない。ブランチも PR も作らない。
- **changed**: 実証済みのドキュメント、ハーネス、マップの修正を 1 件の PR で出荷する。
- **blocked**: カバレッジを完了できなかった、または実証済みの修正を安全に出荷できなかった。何が阻害したかを正確に述べる。

## 編集の範囲

編集してよいのは、検証スキル自身のディレクトリ(その SKILL.md、features/、そのスキルが所有するハーネススクリプト)だけです。実行中にプロダクトコードを編集してはいけません。マップが記述している動作をアプリがもう行わない場合、それはドキュメントのずれ(マップを直す)かプロダクトのリグレッション(報告する。ドキュメントで取り繕わない)のどちらかです。

## パス

0. **対象の特定。** 保守する検証スキルを探します。起動と操作のセクション、および機能マップを本文に持つ、プロジェクトローカルのスキルです(たいていは `.cursor/skills/verify-*/`)。候補が複数ある場合はどれかを尋ねます。ない場合は、対象を捏造せず、停止して `/create-verification-skill` を案内します。

1. **インデックスの整理。** 機能マップの README を読み、同じ階層のファイルを glob します。欠落、余分、重複、リンク切れのエントリを直します。軽い作業にとどめ、一覧を自動生成することはしません。

2. **ソースウェーブ。** 機能ファイル 1 つにつき、読み取り専用のサブエージェントを 1 つ、並行して起動します。各サブエージェントは「このユーザー向け機能はどう動いているか」をソースから説明し、ドキュメントのずれの疑いを引用付きで指摘し、ライブ検証の手順を 1 つ簡潔に返します。子はアプリを操作せず、ファイルも編集しません。返却の形式は、機能の要約 / ソース上の入口 / ずれの疑い(なければ「なし」) / 手順 1 つ、です。

3. **突き合わせ。** すべての機能ファイルについて、返却された要約があることを確認します。重なる手順は、現実的な範囲で、できるだけ少ないアプリ状態にまとめます。引用されたずれはスポットチェックし、問題なしとされた主張を改めて証明し直すことはしません。最近の変更を洗い、マップに載っていないユーザー向けの面がないか確認します。「載っていない」と判断するには、具体的なソースのパスが必要です。

4. **ライブパス。** ソースが問題なさそうでも必須です。操作はすべてコーディネーターが担います。起動の方式は検証スキル自身のものに従います。サーバーや UI なら、長寿命の 1 インスタンスを直列に操作します。短命な CLI なら、操作ごとに分離した新しいセッションを使います。どちらにするかは、このスキルではなく、検証スキルの Launch セクションが決めます。すべての機能を少なくとも 1 回は操作します。また、失敗の種類にかかわらず、パスの間ずっと次の 3 つの不変条件を保ちます。
   1. 直近で予期しない挙動をしたあと、ヘルスチェックしていないインスタンスは操作しない。最初の操作の前に doctor を実行する。セッション単位で運用する場合は、新しいセッションごとに doctor を実行する。失敗した操作のあとにも、もう一度 doctor を実行する。プロセスは正常なのに UI が固まっているなど、doctor では失敗が見えない場合は、期待に頼らず、既知の状態にリセットするか再起動する。
   2. ここまでに取得した証跡は、どのクリーンアップを経ても残る。残っていると仮定せず、名前を付けた保存場所で実際に確認する。
   3. 操作が起動したものは、その操作が役に立つ間より長く生き残らせない。失敗した試行の残骸は、セッションが固まっていても、終了していても、共有されていても片付ける。共有インスタンスの場合は、インスタンスではなく残骸を片付ける。

   スキルのずれが原因の doctor 失敗は、ずれとして扱います。編集範囲の中で直し、修正で無効になったものだけを再起動して、一度だけ再試行します。それでも失敗した場合にはじめて、パスを `blocked` とします。到達できない機能は、具体的な前提条件(認証、権利、OS、外部の状態)と、試みた経路を示した場合に限り、`verified-unreachable` とします。マップがその前提条件を省いているなら、それもずれです。トリアージで出たハーネスの修正は、出荷する前に、必ずライブで再度操作して確かめます。最後の後片付けは、再確認の操作も含め、実行中の最後の操作のあとに行い、実行より長く生き残るものが何もない状態にします(証跡は、スキルの定めに従って残します)。

5. **トリアージ。** ユーザー視点の記述が誤っている、または欠けている場合は、ドキュメントのずれです。直します。動作しているのにハーネスが操作できない場合は、ハーネスのギャップです。直します。ハーネスの修正は、生成時と同じヘルパーの規則に従います(スクリプトは実行可能にし、呼び出し方をスキル本文に書く)。アプリの動作が実際に壊れている場合は、プロダクトのギャップです。ユーザー向けに記録し、この PR には含めません。

6. **出荷か停止か。** changed の場合は、実証済みの修正を 1 件の PR にまとめ、その前に、変更したすべてのファイルを読み直します。clean または blocked の場合は、PR を作らず、結果とカバレッジを正直に報告します。

簡潔な実行メモ(カバーした機能、到達できなかった前提条件、確認済みのずれ、結果)は、スクラッチ用の場所に残します。コミットはしません。
